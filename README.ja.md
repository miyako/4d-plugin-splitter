# Splitter

[English](README.md) | [日本語](README.ja.md)

[`miyako/4d-plugin-splitter`](https://github.com/miyako/4d-plugin-splitter) で開発している、4D 用のネイティブなテキスト処理ツールキットです。
M1（最初の実装マイルストーンの意味で、Apple M1 とは無関係）では、
ネイティブ互換のリテラル分割、リテラル区切り文字リスト、
リソース上限付きの ICU 正規表現分割、オプトイン方式の拡張書記素クラスタ分割を実装しています。
CSV/TSV やその他のツールキット機能は今後のマイルストーンで扱う予定であり、**実装済みの API ではありません**。

Splitter は [MIT ライセンス](LICENSE) です。配布バンドルには、プロジェクトのライセンスに加えて、
ICU/データおよび 4D Plug-in SDK の完全なライセンス表記が
`Contents/Resources/licenses/` に同梱されています。

## インストール

[Releases](https://github.com/miyako/4d-plugin-splitter/releases/latest) からダウンロードしてください。
各リリースには `Splitter-X.Y.Z.dmg` と `Splitter-X.Y.Z.zip` があり、どちらにも**同一の
クロスプラットフォーム `Splitter.bundle`** が入っています。中身は macOS 用ユニバーサル（arm64/x86_64）バイナリ
（Developer ID 署名・公証済み）と Windows x64 バイナリ（Authenticode 署名なし）です。
どちらのアーカイブもどちらのプラットフォームで使えるので、Mac でダウンロードして
バンドルを Windows にコピーしてもかまいません。DMG にはステープルが付いていますが、ZIP には付いていません。
v0.1.3 までのリリースは macOS 専用と Windows 専用のパッケージを別々に配布していました。
それらのリリースの macOS パッケージは Windows では読み込まれません。
通常の push/PR ビルドは、これまでどおりプラットフォームごとの未署名 Actions アーティファクトです。
新しいリリースは、手動実行の **Build** ワークフローが検証後にマージ・署名・公開します。
署名済みダウンロードは、リリースに添付された外部ファイル `signing-provenance.json`、`SHA256SUMS`、
および macOS の署名で検証してください。バンドル内部の `build-manifest.json` は、意図的に
未署名の macOS 入力の来歴を記述しています。未署名専用の `scripts/unpack.py` は署名済み ZIP を受け付けません。
ホストを終了し、ZIP を展開するか DMG を開いて、**`Splitter.bundle` 全体**を
ホストプロジェクトの `Plugins/` フォルダーにコピーし、再起動してください。

```text
Host/
  Project/
  Plugins/
    Splitter.bundle/
      Contents/
        MacOS/Splitter              # macOS: arm64 + x86_64
        Windows64/Splitter.4DX      # Windows: x64
        Resources/
          manifest.json
          constants.xlf
          icudt79l.dat
          licenses/
          dependencies.lock.json
          build-manifest.json
```

各プラットフォームのパッケージには、そのプラットフォームの実行ファイルディレクトリが含まれます。
プライベートな ICU 79.1 のコードは静的リンクされており、対応する完全なセグメンテーションデータと
上流のライセンス表記一式が同梱されています。実行時に何かをダウンロードすることも、OS やホストの ICU を使うこともありません。
データが欠けている場合、正規表現/書記素の呼び出しは Null を返して失敗します。ネイティブのリテラル分割は
このデータに依存しません。

コンポーネント、名前空間ファサード、CLI サブプロセス、コンポーネント専用のプラグインローダーは
いずれも使用していません。コマンドはホストのグローバルなプラグインコマンド空間を占有します。
ホストに `Split_string_Ex` という既存コマンドやプラグイン ID 20371 がないか確認してください。
クリーンなテスト環境で問題がなかったからといって、任意のインストール環境で重複がないとは言えません。

## API

マニフェスト：**`Split_string_Ex(&T;&T;&L;&J):C`**

```4d
$parts:=Split_string_Ex($text; $separator)
$parts:=Split_string_Ex($text; $separator; $nativeOptions)
$parts:=Split_string_Ex($text; $separator; $nativeOptions; $extensions)
$parts:=Split_string_Ex($text; $pattern; sk mode regex)
$parts:=Split_string_Ex($text; ""; sk mode graphemes)
```

モードビットを指定しなければ、最初の 3 つの引数は、**ドキュメントに記載したリソース上限の範囲内で**
ネイティブの `Split string` と同じ動作をします。テキストの区切り文字は文字列全体としてリテラルに扱われ、
パターンや文字の集合としては解釈されません。空の区切り文字は、書記素分割ではなく、
ネイティブと同じ UTF-16 コード単位での分割になります。ネイティブのフラグは変わりません：
`sk ignore empty strings` = 1、`sk trim spaces` = 2、両方で 3。

独自定数 `sk mode regex` = 4 と `sk mode graphemes` = 8 を第 3 引数に指定すると、
拡張モードを選択できます。ネイティブのフラグに足して使います。例：
`sk mode regex+sk trim spaces+sk ignore empty strings`
両方のモードビットを指定すると正規表現分割になり、ワイルドカードのドットが書記素単位で動作し、
`sk trim spaces` を指定した場合は Unicode に基づく空白除去が行われます。
区切り文字リスト、`maxSplits`、正規表現フラグ、より低いリソース上限を指定するには引き続き Object を使いますが、
モードを選ぶだけなら Object は不要になりました。

| モード | 選択方法 | `sk trim spaces` の動作 |
| --- | --- | --- |
| リテラル / リテラルリスト | モードビットなし、Object は任意 | 4D ネイティブの空白除去 |
| 正規表現 | `sk mode regex` または `mode:"regex"` | 4D ネイティブの空白除去 |
| 書記素 | `sk mode graphemes` または `mode:"graphemes"` | クラスタごとに Unicode `White_Space` を除去 |
| 正規表現 + 書記素 | 両方のモードビット | 結果のフィールドごとに Unicode `White_Space` を除去 |

第 3・第 4 引数は省略できます。確認した 20.7 のコンパイラーでは、プラグイン引数を省略すると
警告 533.4 が出ますが、コンパイルは成功します。コンパイル済みコードで実際に省略した場合の動作もテストしています。
末尾の Variant 型引数は同じようには振る舞**わない**ため、第 4 引数はあえて Variant ではなく Object にしています。
区切り文字の Collection は、第 4 引数に直接渡すのではなく、**その Object の中に**入れて渡してください。

コンパイル済みコードでは、ホストが第 4 引数に直接渡された Collection を拒否します。インタープリターでは、
この誤った構造型がプラグインに届く前に null の Object 参照へ変換されることがあり、
その場合は省略と区別できません。サポートしているのは Object または Null のみです。4D がすでに変換した型を
プラグイン側で元に戻すことはできません。

**成功時は実際の Collection（有効な空の Collection を含む）を返します。
失敗時は Null だけを返します。** `.length` を使ったりループで回したりする前に、必ず確認してください：

```4d
$parts:=Split_string_Ex($text; ","; sk mode regex)
If ($parts=Null)
    // 呼び出し側で失敗を処理する
Else
    // Collection を使う（正当に空の場合もある）
End if
```

最後のエラーを取得するコマンドや状態、診断用の Object、オプションの書き換え、
`ON ERR CALL` の呼び出し保証はいずれもありません。この意図的に単純な仕様では、無効なオプション/パターン、
リソース不足、ICU データの欠落、ネイティブ側の失敗を区別しません。
C++ の例外はプラグインの境界で捕捉されます。

### 拡張 Object

| プロパティ | 意味 |
| --- | --- |
| `mode` | `"literal"`（デフォルト）、`"literals"`、`"regex"`、`"graphemes"` のいずれか |
| `separators` | 空でない Text の区切り文字の Collection。`mode` がなければリストモードになる |
| `maxSplits` | 0 以上の整数。区切り文字を最大 N 個まで消費し、残りはそのまま保持する |
| `regexFlags` | 明示的な Boolean のマッチングフラグを持つ Object。正規表現モード専用 |
| `limits` | 後述のリソース上限を引き下げる Object |

未知のキー、メンバーの型の誤り、矛盾する設定、上限の引き上げはいずれも Null を返します。
第 4 引数が空の Object または Null の場合は、ネイティブの動作のままです。
拡張モードで使えるネイティブフラグの組み合わせは 0/1/2/3 のみです。
ホストにネイティブフラグを渡す前に、モードビットは取り除かれます。
既存の呼び出し側のために、Object の `mode` も引き続きサポートしています。モードビットと
明示的な `mode` の両方を指定する場合は、一致している必要があります。両方のビットの組み合わせは
`"regex"` と一致するものとみなします。区切り文字リストはどちらのモードビットとも併用できません。

### リテラルリストと分割回数の上限

リストモードでは、第 2 引数の Text を空にする必要があります。区切り文字は Object の Collection で指定します。
**最も早く出現する位置**を優先し、同じ位置なら**最も長く一致する区切り文字**、それでも同点なら
Collection 内の順序で決まります。
空のメンバーは無効です。空の Collection を渡すと、元の文字列が分割されずに返ります。

```4d
$parts:=Split_string_Ex("a---b::c"; ""; 0; {separators: New collection("-"; "---"; "::")})
// ["a","b","c"]

$parts:=Split_string_Ex("a,b,c"; ","; 0; {maxSplits: 1})
// ["a","b,c"]。残りを捨てて ["a","b"] になることはない
```

`maxSplits:0` は、明示的な空白除去/フィルタリングの前に、元の文字列を分割せずに返します。
入力が空の場合は空のフィールドが 1 つ返ります。この拡張を明示的に指定しない限り、
空の入力や空の区切り文字に対するネイティブの動作は変わりません。

### 正規表現

第 2 引数がパターンとして扱われるのは、`sk mode regex`
または従来の Object 設定 `mode:"regex"` を指定した場合**だけ**です。
M1 では、区切り文字やキャプチャグループは結果に含まれません。

```4d
$names:=Split_string_Ex("Bois-Joli / Morne-à-l’eau"; "\\s*/\\s*"; sk mode regex)
// ["Bois-Joli","Morne-à-l’eau"]

$tokens:=Split_string_Ex("Bois-Joli Morne-à-l’eau"; "[-’\\s]+"; sk mode regex)
// ["Bois","Joli","Morne","à","l","eau"]
```

`regexFlags` の Boolean キー：`caseInsensitive`、`multiline`、`dotAll`、`comments`、
`unicodeWords`、`unixLines`。これ以外のキーや Boolean 以外の値は失敗になります。
サポートしていない正準等価フラグは公開していません。

空のパターンなどの幅ゼロのマッチは、Unicode コードポイント単位で安全に先へ進みます。
出力用のカーソルは別に管理しているので、元のデータは損なわれません。先頭/末尾の
空フィールドは、ネイティブのオプションで指定しない限り保持されます。
`maxSplits` は幅ゼロのマッチも含めて、マッチした区切り文字の数を数えます。残りの部分は、
指定された空白除去/フィルタリングの前にそのまま保持されます。

### 正規表現 + 書記素

```4d
$parts:=Split_string_Ex("e"+Char(769)+"👩‍💻x"; ".{2}"; sk mode regex+sk mode graphemes)
// ["","x"]：区切り文字が書記素クラスタ 2 つを丸ごと消費する
```

文字クラスの外にあるエスケープされていない `.` は、`\X` と同じように拡張書記素クラスタを 1 つ消費しますが、
ドット本来の改行の除外ルールは有効なままです。CRLF がワイルドカードのドットによって途中まで
消費されることは、`unixLines` を指定した場合も含めて、決してありません。
`regexFlags.dotAll` やスコープ付き/インラインの `(?s)` を使えば、改行のクラスタにもマッチします。
エスケープされた `\.`、文字クラス内のドット、`\Q...\E` で囲まれたテキスト、正規表現の
コメントは変更されません。非キャプチャグループで展開するので、キャプチャ番号や
量指定子の結び付きは保たれます。それ以外の正規表現要素や幅ゼロの前進は ICU の
通常の動作のままです。すべての要素のマッチ単位が変わるわけではありません。
明示的な `\X` は、ドットのフラグとは無関係に改行のクラスタにもマッチします。
後読みで可変長の `\X` が使えないなど、ICU の制約はそのまま適用されます。
パターンの上限は、内部で展開した後ではなく、呼び出し側が渡した元のパターンで数えます。
通常の正規表現モードと同様、結果に含まれるのはマッチした区切り文字の**間**にあるフィールドであり、
マッチしたクラスタではありません。

`sk trim spaces` を指定すると、組み合わせモードでは結果の各フィールドから先頭/末尾の Unicode `White_Space`
（ICU 正規表現の `\s` と同じ集合）を取り除きます。パターンにワイルドカードのドットがなくても同様です。
これには U+3000 の全角スペース、NBSP、タブ、改行が含まれます。フィールド内部の空白は保持されます。
マッチングは常に空白除去前の元の文字列に対して行われるため、アンカー、先読み/後読み、区切り文字のマッチ、
`maxSplits` のカウントは変わりません。残りの部分はマッチングの後でのみ空白除去され、
候補フィールド数/出力量の上限は空白除去/フィルタリングの前に適用されます。
空白だけのフィールドは空文字列になり、`sk ignore empty strings` は空白除去の**後**で
それらを取り除きます。空白除去を指定しなければフィールドは変更されず、ignore だけを指定した場合は
もともと空だったフィールドだけが取り除かれます。

```4d
$parts:=Split_string_Ex("　やや　。、 ご機嫌　、斜め。"; "[、。]"; sk mode regex+sk mode graphemes+sk trim spaces+sk ignore empty strings)
// ["やや","ご機嫌","斜め"]
```

**互換性に関する変更：** 以前の組み合わせモードは空白除去を 4D に任せていました。
現在はより多くの種類の空白を取り除くため、ignore も指定している場合は返るフィールドが
少なくなることがあります。通常の正規表現モード、リテラルモード、リストモードは 4D ネイティブの動作のままです。
書記素モード単体での Unicode 空白除去も変わりません。

### 書記素

第 2 引数を空にして、明示的にオプトインします：

```4d
$clusters:=Split_string_Ex($text; ""; sk mode graphemes)
```

バージョンを固定した ICU の文字境界判定により、拡張書記素クラスタを実装しています。サロゲート
ペア、分解された結合アクセント、ZWJ 絵文字、肌の色の修飾、地域指示子による国旗、
CRLF はそれぞれひとまとまりのまま保たれます。空の入力に対しては空の Collection を返します。
正規化は行わず、結果は元の文字列の部分文字列そのものです。
このモードでは、`sk trim spaces` はフィールドごとに Unicode `White_Space` 文字（ICU 正規表現の `\s` と
同じ集合）を取り除きます。タブ、改行、ノーブレークスペース、全角スペースも対象です。
空白除去の結果、空白だけだったフィールドは空文字列になります。
それらを取り除くには `sk ignore empty strings` を追加してください。どちらのフラグも入力は変更しません。
書記素モードでは `maxSplits`、区切り文字リスト、正規表現フラグは無効です。

ネイティブのリテラル分割、リテラルリスト、通常の正規表現モードでは、実際のホストの空白除去/フィルタリング規則を使います。
ASCII や Unicode の空白を推測して近似しているわけではありません。
内部の範囲は 0 始まりの UTF-16 範囲で、確認したホストの 1 始まりの `Substring` の位置に
変換されます。M1 ではトークンの位置情報は公開していません。コード単位、
コードポイント、書記素クラスタは互換ではありません。

## リソース制御

上限は引き下げることしかできません。いずれも正の整数です。

| `limits` のキー | 絶対上限 |
| --- | ---: |
| `maxInputUnits` | UTF-16 で 16,777,216 単位（第 2 引数の Text にも適用） |
| `maxPatternUnits` | UTF-16 で 65,536 単位 |
| `maxItems` | 候補フィールド 100,000 個 |
| `maxOutputUnits` | 候補フィールド全体で UTF-16 33,554,432 単位 |
| `regexSteps` | ICU の処理上限単位で 1,000 |
| `regexStackBytes` | ICU のバックトラック用ヒープ領域 8,388,608 バイト |
| `operationBudgetMs` | 協調的にチェックされる合計予算 5,000 ミリ秒 |

さらにリストでは、区切り文字は最大 256 個、区切り文字の合計は 65,536 単位までです。
`maxSplits` は 0 以上の 32 ビット整数に収まる必要があります。
候補の上限は空白除去や空フィールドの除外の**前**に適用されます。そのため、フィルタリング後の
最終的な Collection が小さくなる場合でも、呼び出しが失敗することがあります。

ICU の処理上限単位はエンジンの作業量であり、**実時間のミリ秒を保証するものではありません**。
合計のチェックはステップの合間に行われ、ホストコマンド 1 回、パターンのコンパイル、
ブロックされたネイティブ呼び出しの途中で割り込むことはありません。プロセス分離や
厳密な実時間タイムアウトではありません。

## ビルドと検証

CMake 3.24 以降、C++17 コンパイラー、スクリプト用に Python 3.12 以降が必要です。
依存関係は [`dependencies.lock.json`](dependencies.lock.json) で不変・チェックサム付きで固定されています。
パッケージマネージャー、外部のランタイムプロセス、ホストの ICU は不要です。

```sh
cmake -S . -B build/universal -DCMAKE_BUILD_TYPE=Release \
  '-DCMAKE_OSX_ARCHITECTURES=arm64;x86_64' -DCMAKE_OSX_DEPLOYMENT_TARGET=12.0
cmake --build build/universal --parallel 2
ctest --test-dir build/universal --output-on-failure
python3 -m unittest discover -s tests/python -v
python3 scripts/package.py --build-dir build/universal --output dist/Splitter-macos-universal.zip
python3 scripts/unpack.py dist/Splitter-macos-universal.zip build/unpacked
python3 scripts/test_m1.py --tool4d /path/to/tool4d.app/Contents/MacOS/tool4d \
  --plugin build/unpacked/Splitter.bundle --report build/host-report.json
```

4D 21 以降のホストでは `--preemptive` を付けると、コンパイル済みの 8 プロセスでのストレステストと、
`Process info` による実際の実行モードの確認が必須になります。
このフラグがない場合、レポートにはプリエンプティブのチェックを実行しなかったことが明記されます。
ベースラインの 20.7 用テスト環境では、これらの新しいコマンドを使うテストメソッドは除外されています。

Windows x64 では `cmake -S . -B build -A x64` の後、
`cmake --build build --config Release` と `ctest --test-dir build -C Release` を実行します。
`dumpbin` が使えるよう、パッケージングは MSVC の開発者環境で実行してください。
静的 CRT と ICU のコードは非公開のままで、エクスポートされるのは SDK のエントリーポイントだけです。

パッケージャーは再ビルドを行い、アーキテクチャ、外部依存、エクスポート、
対応するデータとライセンス表記を確認し、ソース/バイナリのハッシュとツールチェーンの
来歴を記録します。ZIP の展開時には、パス、パーミッション、ファイルのハッシュを検証します。
通常のビルドパッケージは未署名です。これらはローカルファイルまたは Actions アーティファクトであり、
自動的に公開されるリリースではありません。手動で公開した v0.1.0 のダウンロードについては
[インストール](#インストール) を参照してください。

`scripts/fetch_host.py` は公開されているホストを**新しい隔離されたディレクトリ**に復元し、
アーカイブの SHA-256 とホストのバージョンの両方を
[`tests/tool4d.lock.json`](tests/tool4d.lock.json) と照合します。ダウンロード URL は変わることがあるため、
チェックサムが変わった場合は、新しいホストを黙って受け入れるのではなく失敗します。オプションの
`--cache-dir` はアーカイブだけをキャッシュし、復元のたびにチェックサムを検証します。
ホスト自体は Splitter に同梱されていません。
macOS では、バージョンの識別に固定したバンドルの plist を使います。21.1 の
`--version` コマンドは、ホスト型ランナー上でバージョンを表示した後にクラッシュしたためです。
メタデータの検証だけでは実行時の互換性は確認**できません**。実際にソース/コンパイル済みの
ホストで実行し、正常に終了してすべてのアサーションに合格する必要があります。

[`native.yml`](.github/workflows/native.yml) は macOS 用ユニバーサルパッケージをビルドし、
ネイティブの arm64 ホストとネイティブの Intel ホストでチェックし、Windows x64 のビルド/テストも行います。
Intel のジョブでは、arm64 のジョブが作成した**同じユニバーサルパッケージ**をチェックします。
さらに、ネイティブの Intel ツールチェーンで独立したビルド/テストも行います。別の
macOS 26 arm64 のジョブでは、固定した 21.1 上で、同じパッケージを実際にコンパイル済みのプリエンプティブ
プロセス 8 つでチェックします。3 つのビルドプラットフォームすべてで、固定した 20.7 上の
インタープリター/コンパイル済みの動作をチェックします。依存関係のキャッシュに入っているのはチェックサム検証済みのソース/ホストのアーカイブであり、
コンパイル済みライブラリや認証情報ではありません。ビルド/署名用の Actions は不変のリビジョンと
読み取り専用の権限を使い、通常のビルドが署名用シークレットを受け取ることはありません。
ビルドはプルリクエストと main への push で実行され、フィーチャーブランチへの push で重複してジョブが走ることはありません。
リリースに署名して公開できるのは、別の手動実行の **Build** パイプラインだけで、
push/PR のチェックにはできません。生成されたパッケージ、ホストのインストール、
継続的な CI の証跡は、無視対象の `build/`/`dist/` か Actions アーティファクトに置かれます。
リポジトリに含まれる小さな JSON レポートは、当時の来歴をそのまま保持しています。

### バージョンの準備

**main** から **Bump version**（[`bump-version.yml`](.github/workflows/bump-version.yml)）を手動で実行し、
`patch`（デフォルト）、`minor`、`major` のいずれかを選びます。このワークフローは `CMakeLists.txt` の
厳密な `X.Y.Z` 形式のバージョンを検証し、`cmake/Info.plist` にある 2 つのバンドルバージョン欄と、
`scripts/package.py` にあるパッケージ来歴のバージョンが一致していることを要求します。
4 つの欄はまとめて更新されます。公開済みのダウンロードリンクや
過去の証跡は変更されません。対象の `vX.Y.Z` にすでにタグがある場合は拒否し、
バンプの実行を直列化し、強制なしで main にコミット/push します。
使うのは `contents: write` 付きの `GITHUB_TOKEN` だけです。リポジトリ/ブランチのルールで
このボットによる push を許可しておく必要があります。PAT や追加のシークレットは不要です。

バンプでは**タグ、ビルド、リリースは作成されません**。`GITHUB_TOKEN` による push では
main への push のビルドが起動しないため、新しいコミットの main から別途 **Build**
（[`build.yml`](.github/workflows/build.yml)）を実行してください。
この 1 回の実行で、すべてのビルド、テスト、署名/公証、リリースの公開を行います。
実行 ID をコピーする必要も、署名のために 2 回目の実行をする必要もありません。
古いバンプの実行で push が拒否された場合は、最新の main から再実行してください。

### ビルド、署名、リリース

バンプの後、Actions → **Build** → **Run workflow** を開き、**main** を選択して
1 回実行します。タグがすでに存在するバージョンは拒否し、再利用可能な
[`native.yml`](.github/workflows/native.yml) で両プラットフォームのビルド/テストを行い、
**すべてのネイティブチェックと実ホストでのチェックが成功した後に限り**
[`sign-macos.yml`](.github/workflows/sign-macos.yml) を呼び出します。このジョブは 2 つの未署名パッケージを検証し、
共有リソースがバイト単位で同一であることを確認したうえで、`Contents/Windows64/Splitter.4DX` を
ユニバーサルバンドルにマージし、単一のクロスプラットフォームバンドルに署名して公証します。どちらも同じ実行コミット・同じ実行を使います。ネイティブの
ジョブは読み取り専用の権限で、署名用シークレットは持ちません。署名ジョブが受け取るのは
既存の 6 つの署名用シークレットだけです。認証情報が欠けている場合や、署名・公証に失敗した場合は
実行が失敗し、公開されません。

最後の隔離されたジョブで、パッケージのハッシュ、ソース/実行の来歴、
公証が受理されたことを検証し、実行コミットに `vX.Y.Z` を作成して、
`Splitter-X.Y.Z.dmg` と `Splitter-X.Y.Z.zip`（同じクロスプラットフォームバンドル）、外部ファイルの
`signing-provenance.json` と `SHA256SUMS` を含む GitHub リリースを公開します。`contents: write` を
受け取るのはこのジョブだけです。PAT やタグをトリガーとするワークフローではなく、`GITHUB_TOKEN` を直接使います。
リポジトリのタグルールで、バージョンタグの作成を許可しておく必要があります。
タグやリリースが置き換えられることはありません。タグの作成に成功して公開に失敗した場合は、
失敗した実行を確認したうえで、そのリリースを手動で仕上げてください。Build を再実行すると、
既存のタグは意図的に拒否されます。

署名の出力と診断ログは Actions アーティファクトとして引き続き入手できます。
DMG にはステープルが付いていますが、ZIP には付いていません。内部のビルドマニフェストは変更されず、
未署名の macOS 入力を記述しています（マージした Windows バイナリは `signing-provenance.json` の
`windowsInput` に記録されます）。署名済み ZIP は未署名専用の `unpack.py` の検証には意図的に
失敗するので、代わりに外部の署名来歴と macOS の署名で確認してください。

必要なリポジトリシークレットの名前：`APPLE_DEVELOPER_ID_CERTIFICATE`、
`APPLE_DEVELOPER_ID_CERTIFICATE_PASSWORD`、`KEYCHAIN_PASSWORD`、
`NOTARYTOOL_APPLE_ID`、`NOTARYTOOL_PASSWORD`、`NOTARYTOOL_TEAM_ID`。
ローカルのシークレット設定ヘルパーを実行するのはユーザー本人だけです。通常の push/PR のビルド/テスト
CI はこれらのシークレットに依存しません。署名/公証の成功を確認するには、認証情報を使った実際の
実行が必要です。[v0.1.0 の署名実行](https://github.com/miyako/4d-plugin-splitter/actions/runs/42151065472) では、
手動で公開する前に、両方の公証が Accepted となって成功しました。

### 検証の証跡とサポート範囲

対象とする互換環境：**4D 20.7 LTS 以降**、macOS ユニバーサル（arm64/x86_64）、
Windows x64。macOS バイナリは 12.0 以降を対象としています。これは、今後のすべての 4D や OS の
リリースで動作することを包括的に保証するものではありません。macOS 12.0 での最小実行環境や GUI の
ワークフローはテストしていません。下の表は過去のローカル実行の記録であり、
[v0.1.0](https://github.com/miyako/4d-plugin-splitter/releases/tag/v0.1.0) にまとめた後のリリース検証ではありません。

| 確認したホスト（macOS 26.7） | 実行方式 | ソース / コンパイル済み |
| --- | --- | --- |
| [20.7 build 20.101905、arm64](tests/evidence/m1-macos-arm64-20.7.json) | ネイティブ | 各モードで 1,294 アサーション合格 |
| [21.1 build 21.100468、arm64](tests/evidence/m1-macos-arm64-21.1.json) | ネイティブ | 各モードで 1,294 アサーション合格 |
| [20.7 build 20.101905、x86_64](tests/evidence/m1-macos-x86_64-translated-20.7.json) | Rosetta による変換 | 各モードで 1,294 アサーション合格 |
| 実機の Intel / Windows x64 | CI は設定済み、ここでは未実行 | 主張しない |

ネイティブのコアは、arm64 と変換実行の x86_64 スライスの両方で、8 スレッドのストレステストを含む
31,185 項目のチェックに合格しました。変換実行はネイティブの Intel での検証ではありません。
リモートのプラットフォームでの結果やダウンロード可能な証跡は
[ネイティブワークフローの実行](https://github.com/miyako/4d-plugin-splitter/actions/workflows/native.yml) で確認できます。
これらの追加の確認として有効なのは、完了して成功したジョブだけです。

ホスト用のテストランナーは、実際にインタープリターとコンパイル済みで実行されたこと、各モード 1,248 ケースでの
ネイティブとの一致、Unicode/正規表現/リスト/エラー/上限に関する拡張ケース、
繰り返し実行時の所有権、データの欠落/切り詰め時にホストの ICU へフォールバックせず明示的に失敗することを
アサートします。ソース/コンパイル済みのモードを、起動フラグだけから推測することはありません。
本番のマニフェストでは、ユーザーの明示的な要望により **`threadSafe:true`** を有効にしています。
この宣言はプリエンプティブでの使用を許可するものであり、それ自体がブリッジの安全性を
証明するものではありません。上記のレポートは、以前の `threadSafe:false` のパッケージの来歴を
保持しています。`--preemptive` を付けると、ホスト用のテストランナーはさらに、
コンパイル済みのプリエンプティブプロセス 8 つをチェックし、実際の実行モードを確認し、
4 つの分割モードすべて、失敗の分離、ICU の初回使用時の並行初期化を
テストします。
有効化したパッケージの新しいレポートでは、[ネイティブ arm64 の 20.7](tests/evidence/m1-threadsafe-macos-arm64-20.7.json)
と [ネイティブ arm64 の 21.1](tests/evidence/m1-threadsafe-macos-arm64-21.1.json) で、
各モードのソースとコンパイル済みでそれぞれ 1,294 アサーションが記録されています。
21.1 の実行では、さらに実行時にプリエンプティブであることを確認した 8 プロセスで
9,600 アサーションに合格しました。20.7 の実行ではプリエンプティブ実行を検証して**いません**。
このコンパイラーは新しい `Process info` による確認に対応していないためです。
この限られた macOS での証跡は、ブリッジの安全性を一般的に保証するものではありません。
これらのローカルレポートは、Windows、ネイティブの Intel、20.7 でのプリエンプティブ
対応を示すものではありません。リモートのプラットフォームでの確認結果は、対応する CI の証跡を参照してください。

以前の SDK の調査結果は、現在の障害ではなく過去の記録として `tests/evidence/` に残しています：
Variant の省略は失敗する、型指定した Longint と Object の省略は警告のみでコンパイルが成功する、
SDK のアサーションはホストのハンドラーを呼び出さない、というものです。過去の調査用プローブは
`-DSPLITTER_BUILD_PROBES=ON` で有効にした場合のみ `build/probes/` に別途ビルドされ、
本番のバンドルに登録されることはありません。

## 今後のツールキット

次のマイルストーンでも、合意済みの範囲を維持します：構造化された位置情報と、区切り文字/キャプチャの保持。
CRLF/LF/CR に対応した行分割と、末尾の空行の扱い。
partition/rpartition と scan/extract。厳密でインクリメンタルな CSV/TSV の**読み込みと
書き出し**、テキストを保持するフィールド、明示的な方言/ヘッダー設定、オプトイン方式の
数式インジェクション対策。ロケールに応じた単語/文の分割と、ドキュメント化された識別子の
規則。再利用可能なコンパイル済みパターンと、上限付きでライフタイムが安全なハンドルを使うバッチ API。
CSV ライブラリのライセンスや CSV の詳細な診断情報については、そのマイルストーンで決定します。
ステミング、暗黙の型変換、パフォーマンス、リリースの準備状況、
実行していないプラットフォームでの動作については、一切主張しません。
